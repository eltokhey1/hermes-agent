# Hermes — نموذج منفصل للموافقات وجذر الثقة (بحثي فقط)

**الحالة: RESEARCH_ONLY · PRODUCTION=HOLD · HITL=REQUIRED · G0/G-CODE/G1=NO-GO.**

## ما نُفّذ بالفعل

هذه الحزمة قابلة للتشغيل، بلا اعتماد على مكتبات خارجية، وتستخدم عمليتي نظام تشغيل منفصلتين في الاختبار:

1. **Root process**: توقّع بداخلها نقاط تحقق HMAC-SHA256 ومخزن epoch مستقل في ملف SQLite مختلف، ولا تُرسل مفتاح توقيع الجذر إلى عملية الموافقات أو الوكيل. الاتصال عبر قناة loopback بمفتاح صلاحية منفصل.
2. **Authority process**: توافق على **معاينة اصطناعية فقط** بعد التحقق من إثبات هوية اصطناعي موقّع، وتحدّي مراجعة (CSRF-like) مرتبط بالجلسة والمهمة ولمرة واحدة، و`exact_action_hash` ومدة الصلاحية. تعمل قناة الوكيل وقناة المالك بمفاتيح وصول مختلفة. واجهة الوكيل لا تتضمن إصدار الموافقات.
3. **قاعدة حالة + سجل أحداث** داخل عملية الموافقات؛ ربط الحالة ببصمة موقّعة تصدر عن عملية الجذر. عند اختلاف قاعدة البيانات ونقطة التحقق أو تعطل عملية الجذر، تتوقف العمليات وتُرفض بدلاً من إعادة المحاولة تلقائيًا.
4. **`ESTOP` تجريبي محفوظ** في حالة الموافقات ومربوط بجذر الثقة. لا يوقف أدوات فعلية أو يعالج إجراء خارجي قيد التنفيذ.
5. **منع التنفيذ مرتين**: تأشير التصريح كمستهلك قبل إرجاع نتيجة معاينة خاملة. إذا توقف النظام بين تحديث قاعدة البيانات والجذر، تُكتشف الحالة غير المتسقة وتُحظر حتى تسوية مستقلة.

## تشغيل آمن داخل بيئة التخلص

من المجلد ذاته، بعد فتحه في بيئة اختبار معزولة:

```bash
python -W error -m unittest -q test_authority
python -W error demo_run.py
```

لا تستخدم هذه الحزمة على قاعدة بيانات Hermes الحقيقية. المثال ينشئ ملفات SQLite **مؤقتة** ويغلق العمليات وينظف الملفات عند انتهاء التنفيذ.

## الأدلة الفعلية

- Python 3.13.5، 21 اختبارًا محليًا: **21 PASS، 0 FAIL، 0 SKIP**.
- تجربة تشغيل منفصلة: عمليتان، قناة الوكيل لا يمكنها الموافقة، وبصمة الإجراء متطابقة، وتصريح الاستخدام لمرة واحدة يعمل، ولا توجد آثار خارجية.
- طبقة البيانات موثقة في `authority.py`، وخدمة العمليتين في `ipc_service.py`، ومصدر الهوية الاصطناعي للاختبار في `test_identity_research.py`.

## ما لم يُثبت — لا يجوز تحويله إلى إنتاج

- **هوية إنسان حقيقية**: رمز الهوية يوقّعه مُصدِر HMAC اصطناعي للاختبار؛ لا توجد مصادقة passkey/WebAuthn/OIDC، أو جلسة HTTPS owner-only، أو تكامل CSRF حقيقي مع متصفح معتمد. تحدي المراجعة في الاختبار ليس ضمان CSRF إنتاجيًا.
- **حماية الحسابات فعليًا**: العمليتان منفصلتان لكنهما تعملان بصلاحيات مستخدم نظام التشغيل نفسها في الاختبار، ويمكن لمالك تلك الصلاحيات الوصول إلى ملفات SQLite، وربما أسرار العمليات. يجب لاحقًا فصل المستخدم/الـVM والملفات والمفاتيح.
- **عداد مستقل غير قابل للتراجع**: مخزن الجذر منفصل عن قاعدة الأحداث لكنه ما زال قابلًا لاسترجاع النسختين معًا. فقط `trusted_min_epoch` الذي تقدمه جهة مستقلة *محميّة فعلًا* يكشف إعادة النسختين؛ هذه الجهة غير موجودة هنا.
- **استعادة Windows الحقيقي P0/P1**: لا يوجد وصول مؤكد إلى جهاز المالك عبر ruOS، ولم تُجرَ نسخة احتياطية أو استعادة فعلية أو اختبار إيقاف حقيقي أثناء تنفيذ أثر خارجي.
- **المصادقة عبر الشبكة**: قنوات `multiprocessing.connection` تعمل على `127.0.0.1` تجريبيًا وليست HTTPS، ولا ينبغي كشفها للعامة. لا يوجد خادم منشور أو تفعيل لأي عملية إرسال أو دفع أو تعديل خارجي.

## ما يلزم لإكمال إعداد الخدمة الحقيقي

1. توفير جهاز/VM مخصص أو حساب نظام تشغيل مقيد مستقل، مع منع وصول الوكيل إلى مفاتيح الموافقة والجذر والـepoch ودليل بياناتهما، واختبار رفض ACL الفعلي.
2. ربط خدمة المالك بمزود هوية موثوق عبر واجهة آمنة؛ الإعداد يحتاج دخول المالك الصريح عبر واجهة الخدمة. استبدال `SyntheticProofVerifier` بمتحقق من رموز مزود الهوية؛ لا يجوز قبول الاسم النصي بدل الهوية.
3. نقل الجذر إلى خدمة ذات صلاحية مستقلة ومعها **سجل epoch غير قابل للتراجع** أو حماية خارجية مكافئة، مع تسلسل تدقيق، وتحديد مسار التسوية الآمنة عند الانقطاع بين تحديث قاعدة الحالة والجذر.
4. ESTOP مستقل عن خدمة الوكيل ومُختبر تحت فشل العملية وفي أثناء إجراء حقيقي، لكن ضمن بيئة قابلة للتخلص، ثم اختبار الاستعادة P0/P1 على جهاز المالك بعد توافره وموافقته.
5. مراجعة مستقلة للأمن، تحديد SHA للاختبار والقبول، واختبار جميع الحالات السلبية، ثم موافقة بشرية منفصلة *لكل فعل خارجي*. حتى ذلك الحين، لا دمج ولا نشر.

## حدود السرية والتكلفة
